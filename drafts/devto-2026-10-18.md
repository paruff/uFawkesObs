## Why

An observability stack that alerts on itself teaches you to ignore alerts. On a
default `make up` of uFawkesObs v1.0.0, about 27 alerts fired even though every
container was healthy and none had restarted. That breaks the promise that the
stack installs cleanly from its README.

## What

v1.0.1 makes a healthy default install quiet. Nothing fires once the stack is
up. The rules were wrong in five different ways, and each is fixed at its source
rather than silenced.

## How

- `dora-api` is scraped through DNS discovery, so it only exists as a target
  while the `dora` profile runs. That removed `ServiceDown` and three SLO
  burn-rate alerts that came from a target that was never meant to be up.
- `ContainerRestarting` now needs the process start time to move by more than
  10 seconds. Docker Desktop's VM clock wobbles it by about one second, which
  tripped `changes()` for every job.
- The DORA `*Absent` guards only apply while `dora-api` is up.
- Rules that used metric names the collector and Prometheus do not export now
  use the real ones, and a retention limit of 0 no longer divides to infinity.
- Two "dropped" alerts used an `absent() * 0` fallback. That returns a series
  with value 0, and an alert fires on any series, so they fired on no data.

## Proof

Fresh clone, README steps, `make up`, 30 minutes: zero alerts on Linux and on
macOS. Before, the same stack had 28 alerts firing or pending. Unit tests cover
the new scrape shape and the DORA guards.

## What's Next

- Give CI a host-metrics source so the Host Metrics dashboard can rejoin the
  data-freshness gate.
- Let a fix PR show the "main is healthy" gate as green when it is the fix.
